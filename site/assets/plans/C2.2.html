C2.2 — BFCL Precondition-Graph Drift: Execution Plan

0. Goal and roster contract

Build an executable BFCL-derived **C2.2** task family.

**Roster contract**

  • Family: `precondition graph`
  • Origin: BFCL pattern
  • Skill store: directed action-precondition graph + planner template
  • Application recipe: topologically order required actions and avoid redundant calls
  • Drift: `edge_add + edge_drop`
  • Topology: expansion / retirement
  • Schedule: abrupt
  • Physical event: **same event as C2.1**
  • C2.1 scope sweep: 10%, 25%, 40% of performance-relevant edges
  • C2.2 evidence:
  • D1 = 0%
  • D2 = 0%
  • D3 = 100%
  • C2.2 construction rule: hide successful traces; revised graph is discoverable only from interaction outcomes
  • Required update: add/tombstone edges, replan, simulator-replay candidate sequences
  • Validation: edge precision/recall, invalid-action rate, redundant calls, discovery cost
  • Readouts: edge RPrec/RRec, IAR, `d*`, CRR

The cleanest BFCL substrate is `VehicleControlAPI`, because its executable backend already has hidden procedural preconditions. For example, engine start currently depends on door state and a fully pressed brake pedal, and cruise control depends on the engine being running.

3. Select the paired C2.1/C2.2 physical event

C2.2 must use the **same physical edge change as C2.1**.

Use a simple 25% pilot:

8 performance-relevant edges
2 changed edges = 25%

Recommended change:

Edge add

Add:

P_parking_brake_engaged → A_start

The new regime requires the parking brake to be engaged before engine start.

Edge drop

Remove:

P_brake_full → A_start

The fully pressed brake pedal is no longer required for starting the engine.

This gives both:

expansion: new parking-brake prerequisite
retirement: old full-brake prerequisite removed

The semantic goal remains:

engine running

For cruise-control siblings, the semantic goal remains:

cruise active at requested speed

but the valid minimal plan changes upstream.

Create:

drift_spec.json

with:

{
  "operator": ["edge_add", "edge_drop"],
  "schedule": "abrupt",
  "scope": 0.25,
  "added_edges": [
    ["P_parking_brake_engaged", "A_start"]
  ],
  "dropped_edges": [
    ["P_brake_full", "A_start"]
  ]
}

Later generate 10% and 40% variants by changing the number of edited edges while preserving the same construction logic.

vehicle_control_c2_r_minus.py

Conceptually:

if self.remainingUnlockedDoors > 0:

5. Build executable `r+`

Create:

vehicle_control_c2_r_plus.py

Modify only the targeted prerequisites.

Remove the obsolete prerequisite

Delete or disable the full brake-pedal checks:

# no longer required in r+

Add the new prerequisite

Add:

if self.parkingBrakeStatus != "engaged":
    return {
        "error": "Parking brake must be engaged before starting the engine."
    }

Keep:

doors locked
fuel condition
engine outcome

unchanged.

This makes the physical drift executable rather than transcript-only.

6. Keep public tool schemas stable

Do not announce the changed prerequisite graph in the normal function documentation.

The API schema should still describe:

startEngine(...)
activateParkingBrake(...)
pressBrakePedal(...)

without saying:

"startEngine now requires parking brake"

because C2.2 has:

D1 = 0

The learner must discover the graph only through interaction outcomes.

7. Build stale and oracle skills

Create:

skill_r_minus.md
skill_r_plus_oracle.md

`skill_r_minus.md`:

# Vehicle Procedure Skill — r-

To start the engine:

1. Lock all doors if needed.
2. Fully press the brake pedal.
3. Ensure fuel is available.
4. Start the engine.

To activate cruise control:

1. Complete the engine-start procedure.
2. Set cruise control.

`skill_r_plus_oracle.md`:

# Vehicle Procedure Skill — r+

To start the engine:

1. Lock all doors if needed.
2. Engage the parking brake.
3. Ensure fuel is available.
4. Start the engine.

The brake pedal is not required for engine start in this regime.

To activate cruise control:

1. Complete the current engine-start procedure.
2. Set cruise control.

Do not expose `skill_r_plus_oracle.md` to the learner.

8. Generate sibling tasks from varied initial states

Create:

siblings.json

Vary the initial state so the changed graph is causally testable.

Affected sibling example — new edge required

Initial state:

doors locked
parking brake released
brake pedal fully pressed
fuel available
engine stopped

User:

"Start the engine."

Stale skill tries:

press brake
start engine

`r+` returns a parking-brake violation.

Correct `r+` plan:

activateParkingBrake("engage")
startEngine(...)

Affected sibling example — dropped edge creates redundancy

Initial state:

doors locked
parking brake engaged
brake pedal released
fuel available
engine stopped

The stale skill unnecessarily presses the brake before starting.

It may remain correct but has higher cost.

This is necessary for CRR.

Propagated affected sibling

User:

"Activate cruise control at 60."

The plan traverses:

startEngine → setCruiseControl

so the upstream changed prerequisite affects this sibling too.

10. Hide all D1 and D2 evidence

C2.2 must not receive:

changelog
updated policy note
successful post-drift traces
accepted demonstrations

Specifically, do not provide a trace such as:

activateParkingBrake → startEngine → success

as learner-visible evidence.

The only source of new-edge information is D3 interaction.

---

11. Build the D3 interaction interface

Create:

d3_interaction.py

It should expose safe execution of actions against `r+` and return normal BFCL responses/errors.

Example:

execute("startEngine", {"ignitionMode": "START"})

may yield:

{
  "error": "Parking brake must be engaged before starting the engine."
}

This observation identifies a missing prerequisite.

Then:

execute("activateParkingBrake", {"mode": "engage"})

followed by:

execute("startEngine", {"ignitionMode": "START"})

succeeds.

For the retired brake edge, the learner must discover redundancy by comparing:

with pressBrakePedal
vs.
without pressBrakePedal

at matched correctness.

Every interaction must log:

task_id
state_before
action
arguments
response
state_after
cost

---

12. Define the intended graph-learning update

Expected learner transformation:

+ P_parking_brake_engaged → A_start
- P_brake_full → A_start

Then replan.

For engine start:

- lock → brake → start
+ lock → parking_brake → start

For tasks where parking brake is already engaged:

- brake → start
+ start

if all other prerequisites already hold.

The method should tombstone the obsolete edge rather than retaining both forever.

---

13. Add simulator replay validation

For every candidate learned graph:

  1. synthesize a plan;
  2. execute it against the `r+` simulator;
  3. reject the graph update if the plan violates the environment;
  4. compare with the oracle minimal plan for redundant-call analysis.

Create:

validation/replay_graph.py

14. Compute graph truth from the regime object

The benchmark must know the exact current graph.

Create:

graph_truth_r_minus.json
graph_truth_r_plus.json

Then compute:

Edge precision

recovered true edges / recovered edges

Edge recall

recovered true changed edges / true changed edges

Handle retired edges explicitly:

a learner that keeps an obsolete edge is not fully correct

---

15. Measure IAR and discovery cost

Invalid-action rate

Count failed calls caused by wrong precondition assumptions.

Discovery cost

Count all D3 actions used to identify the changed graph.

`d*`

Sweep the allowed D3 budget:

1, 2, 4, 8, ...

and find the smallest budget after which held-out affected siblings can be solved reliably.

Do not define `d*` from a single trace.

---

16. Measure CRR on efficiency-sensitive siblings

Use siblings where the stale skill remains correct but redundant.

For example:

r+ initial state:
parking brake already engaged
doors locked
fuel available
brake released

Stale plan:

pressBrakePedal
startEngine

Oracle plan:

startEngine

This creates a nonzero cost gap at matched correctness.

Compute CRR only when:

C_stale != C_oracle

17. Required controls

Run:

A. No skill

Agent discovers procedure from scratch.

B. `r+` oracle skill

Upper bound.

C. Frozen `r-` stale skill

Tests stale damage.

D. `r-` skill + D3 graph learner

Target method condition.

No condition should receive successful post-drift traces.

---

18. Scale to the 10% / 25% / 40% scope sweep

After the 25% pilot works:

  • add more independent precondition-bearing actions;
  • construct a larger graph;
  • edit 10%, 25%, and 40% of performance-relevant edges;
  • keep semantic goals and unrelated edges fixed.

Do not fake percentages by editing decorative edges that never affect a valid/minimal sibling plan.

---

19. Acceptance checklist

  • [ ] `r-` and `r+` are executable BFCL backends;
  • [ ] the same semantic goals are valid in both regimes;
  • [ ] the physical event contains at least one edge addition and one edge retirement;
  • [ ] C2.2 exposes no D1;
  • [ ] C2.2 exposes no D2 successful traces;
  • [ ] all changed edges are discoverable through D3 outcomes;
  • [ ] affected siblings exercise edited edges;
  • [ ] unchanged siblings exercise retained edges;
  • [ ] at least one sibling exposes invalid-action stale damage;
  • [ ] at least one sibling exposes redundant-call/cost stale damage;
  • [ ] oracle plans replay successfully;
  • [ ] recovered graph is scored against exact generator truth;
  • [ ] probe/action discovery cost is metered.
