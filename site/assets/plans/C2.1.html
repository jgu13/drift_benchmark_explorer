C2.1 — BFCL Precondition-Graph Drift: Agent Execution Plan

Objective

Build an executable, BFCL-derived **C2.1 precondition-graph drift family**.

The family tests whether an agent can update a persistent procedural skill when hidden action prerequisites change.

The persistent skill stores:

directed action-precondition graph
+
planner / execution recipe

The learner uses this graph to:

topologically order required actions
+
avoid redundant calls

The physical drift is:

edge_add + edge_drop

with:

topology = expansion + retirement
schedule = abrupt

The C2.1 evidence contract is:

D1 = 0%
D2 = 40%
D3 = 60%

where:

D2 = successful post-drift sibling traces
D3 = violation / counterexample interaction feedback

The full family should support a drift-scope sweep over:

10%
25%
40%

of **performance-relevant precondition edges**.

The initial construction target is:

72 total siblings

32 affected
18 unchanged-retention
14 boundary/open-set
8 matched-null

For the first pilot, implement only a small subset, but preserve the same construction logic.

---

1. Reuse the same physical event as C2.2

C2.1 and C2.2 use the **same `r- → r+` environment change**.

Their difference is:

C2.1:
D2 = 40%
D3 = 60%

C2.2:
D2 = 0%
D3 = 100%

Therefore do not invent a different graph event for C2.1.

Use the same BFCL `VehicleControlAPI` substrate and the same pilot physical event:

ADD:
parking brake engaged → start engine

DROP:
full brake pedal → start engine

This makes C2.1 and C2.2 directly comparable.

4. Define the graph representation

Represent the skill as a directed graph over:

action nodes
+
state-predicate nodes

Recommended action nodes:

A_lock
A_brake
A_park
A_fuel
A_start
A_cruise

Recommended predicate nodes:

P_doors_locked
P_brake_full
P_parking_brake_engaged
P_fuel_available
P_engine_running

An edge:

P_brake_full → A_start

means:

> the full-brake predicate must hold before `startEngine` is valid.

An edge:

A_start → P_engine_running

means:

> successful engine start establishes the engine-running predicate.

8. Build executable regime `r+`

Copy:

vehicle_control_c2_r_minus.py

to:

vehicle_control_c2_r_plus.py

Modify only the chosen prerequisite edges.

Remove the retired edge

Disable the brake-pedal prerequisite for engine start.

For example, remove:

if self.brakePedalStatus != "pressed":
    return {"error": ...}

if self._brakePedalForce != 1000.0:
    return {"error": ...}

from the `r+` start procedure.

Add the new edge

Add:

if self.parkingBrakeStatus != "engaged":
    return {
        "error": "Parking brake must be engaged before starting the engine."
    }

Keep unchanged:

door requirement
fuel requirement
engine-start effect
cruise-control semantics
unrelated vehicle actions

14. Build affected sibling A: new edge required

Use an initial state such as:

doors locked
parking brake released
brake fully pressed
fuel available
engine stopped

User request:

"Start the engine."

Under `r-`, the stale skill is valid.

Under `r+`, the stale plan:

press brake
start engine

fails because:

P_parking_brake_engaged

is missing.

The correct `r+` plan is:

activateParkingBrake(mode="engage")
startEngine(...)

This sibling detects the **added edge**.

---

15. Build affected sibling B: retired edge creates redundant work

Use:

doors locked
parking brake engaged
brake released
fuel available
engine stopped

User:

"Start the engine."

Under `r+`, the oracle minimal plan is:

startEngine(...)

if all remaining prerequisites already hold.

The stale skill may do:

pressBrakePedal(1.0)
startEngine(...)

and still succeed.

This sibling is important because it creates:

same correctness
higher stale cost

which is required for CRR.

16. Build propagated affected siblings

Create tasks where the changed start-engine procedure is upstream of another goal.

Example:

"Activate cruise control at 60."

The dependency path is:

current engine-start plan
        ↓
engine running
        ↓
setCruiseControl(...)

Thus changing an engine-start prerequisite also affects cruise-control planning.

These tasks test whether the learned graph update transfers structurally rather than being memorized as a single engine-start answer.

17. Label sibling obligation support

For every sibling, store something like:

{
  "id": "C2.1-aff-001",
  "semantic_goal": "start_engine",
  "slice": "affected",
  "obligation_support": [
    "P_parking_brake_engaged->A_start",
    "P_brake_full->A_start"
  ]
}

A task is affected iff:

obligation_support ∩ edited_edges ≠ ∅

If the valid and minimal plan does not touch an edited edge, the task belongs in:

unchanged-retention

23. Define the C2.1 evidence obligations

The evidence mix is:

D2 = 40%
D3 = 60%

The split must be over **changed edge obligation weight**, not arbitrary file count.

For the 25% pilot, define edge obligations such as:

O1 = parking brake is newly required before start
O2 = full brake is no longer required before start
O3 = revised start procedure transfers to downstream cruise planning
O4 = obsolete brake call creates avoidable execution cost
O5 = candidate graph update must preserve retained prerequisites

Assign approximate evidence responsibility:

D2:
valid paths and successful consequences
≈ 40%

D3:
violations, failed assumptions, retirement counterexamples,
and causal edge confirmation
≈ 60%

27. Prevent D2 from identifying the entire graph

D2 should cover only its assigned 40% edge weight.

Do not provide successful traces for every edited configuration.

In particular, successful traces alone may not prove that:

P_brake_full → A_start

was retired.

A trace that omits a brake action is evidence, but retirement should be made causally decisive through D3 counterexamples or controlled comparisons.

This preserves meaningful D3 responsibility.

32. Define the intended graph update

P_brake_full → A_start

33. Require candidate-plan replay before skill promotion

After the learner proposes a graph update:

  1. generate a candidate plan from the updated graph;
  2. execute it in the `r+` simulator;
  3. verify final state;
  4. verify no invalid actions;
  5. compare its cost against the oracle minimal plan;
  6. only then promote the new graph into persistent skill.

Do not accept a text-only graph edit without executable replay.

48. Acceptance checklist

An agent rebuilding C2.1 should finish only when:

  • [ ] BFCL `VehicleControlAPI` is used as the procedural substrate;
  • [ ] `G-` is extracted from executable precondition checks;
  • [ ] `G+` changes at least one prerequisite edge and retires at least one edge;
  • [ ] the 25% pilot edits exactly 2 of 8 performance-relevant edges;
  • [ ] the same physical event can be reused by C2.2;
  • [ ] user goals and action effects remain fixed;
  • [ ] public tool docs do not reveal the graph delta;
  • [ ] stale `S-` is retained after drift;
  • [ ] oracle `S+` is created but hidden;
  • [ ] D1 is completely withheld;
  • [ ] D2 successful traces cover approximately 40% of changed obligation weight;
  • [ ] D3 violation/counterexample evidence covers approximately 60%;
  • [ ] D2 evidence siblings are disjoint from evaluation siblings;
  • [ ] D3 interactions are safe and metered;
  • [ ] candidate graph updates are simulator-replayed before promotion;
  • [ ] affected siblings touch edited edges;
  • [ ] unchanged siblings touch only retained edges;
  • [ ] there is at least one invalid-action stale case;
  • [ ] there is at least one correct-but-redundant stale case;
  • [ ] no empirical metric is fabricated before execution.
