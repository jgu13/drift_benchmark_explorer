# D4.1 BFCL Execution Plan

## Objective

Build an AppWorld-pattern D-family efficiency-drift benchmark where a better
path appears after a regime update.

```text
Benchmark ID: D4.1
Semantic package: bulk_tag_app
Drift: action_add
Topology: improvement
Schedule: abrupt
Physical event: one new bulk endpoint replaces 3-5 primitive calls
Evidence allocation: D1 = 50%, D2 = 0%, D3 = 50%
```

The stale workflow remains semantically correct. The post-drift regime adds a
lower-cost action that changes the optimal route for applicable tasks.

artifacts live inside the semantic package. The package is self-contained and

## Drift Definition

Use a compact deterministic contact/tag API.

`r_minus` exposes:

```text
get_contact(contact_id)
add_tag(contact_id, tag)
remove_tag(contact_id, tag)
```

`r_plus` preserves all stale endpoints and adds:

```text
bulk_add_tag(contact_ids, tag)
```

The new endpoint is valid only when:

```text
3 to 5 contact IDs are supplied
all contacts belong to the same workspace
the list contains no duplicate IDs
one shared tag is applied to all listed contacts
```

Cost model:

```text
get_contact = 1
add_tag = 1
remove_tag = 1
bulk_add_tag = 1
```

For 3-5 valid same-workspace contacts, the post-drift optimum is one
`bulk_add_tag` call instead of 3-5 `add_tag` calls. Final semantic state is
identical across regimes.

## Evidence Allocation

Learner-visible evidence is restricted to `bulk_tag_app/evidence/`.

```text
D1: evidence/d1_rule_bulk_add_tag.md
D2: none
D3: evidence/d3_probe_log.jsonl
```

`skill_r_minus.md` is learner-visible stale skill text. `skill_r_plus_oracle.md`
is hidden evaluation-only oracle text and must not be exposed as evidence.

D1 states the new endpoint signature and scope only. It must not claim measured
cost superiority. D3 provides the evidence-only probe showing semantic
equivalence and lower metered cost on a disjoint four-contact probe, plus a
mixed-workspace boundary rejection.

## Sibling Construction

Use `siblings.json` as the canonical task source in manifest form. Build exactly
19 evaluation siblings:

```text
8 affected
4 unchanged-retention
4 boundary/open-set
3 matched-null
```

Use stable underscore-delimited IDs:

```text
D4.1_aff_001 ... D4.1_aff_008
D4.1_ret_001 ... D4.1_ret_004
D4.1_bnd_001 ... D4.1_bnd_004
D4.1_null_001 ... D4.1_null_003
```

Each sibling must include:

```text
id
slice
semantic_goal
obligation_support
question
initial_state
involved_classes
affected
r_minus_ground_truth
r_plus_ground_truth
expected_final_state
expected_cost_r_minus
expected_cost_r_plus
```

Mark affectedness from executable obligation support rather than wording:

```python
affected = (
    gold_or_optimal_trace_intersects_changed_obligation
    or graded_final_output_differs
    or current_optimal_cost_target_changes
)
```

For pure efficiency drift, the final semantic state can remain identical while
the optimal-cost target changes.

Affected siblings cover:

```text
3 contacts same tag
4 contacts same tag
5 contacts same tag
already-tagged subset
compound tag plus later read
different starting workspace page/state
bulk followed by another unrelated update/read
old route remains within cap but is dominated
```

Unchanged-retention siblings cover one-contact add, two-contact add, tag
removal, and a read-only contact lookup. Boundary/open-set siblings cover six
contacts, mixed workspaces, empty contact list, and duplicate IDs. Matched-null
siblings vary wording/order/IDs without creating a bulk-applicable optimal-cost
change.

## Compilation

`compile_d4_1.py` loads `siblings.json`, validates the 8/4/4/3 composition,
and writes:

```text
possible_answer_r_minus.json
possible_answer_r_plus.json
optimal_costs.json
sibling_summary.json
```

Package-level `possible_answer_*` files are the loader-facing answer files.
This repository does not currently include `data/dataloader.py`; if a shared
drift loader is later added, register `D4.1` to point at:

```text
D4.1/bulk_tag_app/siblings.json
```

## Validation

Run:

```bash
python data/D4.1/bulk_tag_app/compile_d4_1.py --write
python data/D4.1/bulk_tag_app/validation/replay_checks.py
bash data/D4.1/bulk_tag_app/validation/test_d4_1_architecture.sh
```

Validation must check:

- JSON parseability for all package JSON artifacts.
- `siblings.json` is a manifest with 19 tasks.
- Exact slice counts are 8/4/4/3.
- All task IDs use the `D4.1_<slice>_<nnn>` convention.
- `r_plus` preserves stale actions and adds only `bulk_add_tag`.
- D1 and D3 evidence files are present and named with `d1`/`d3` prefixes.
- `evidence_allocation.json` states D1=50, D2=0, D3=50.
- The oracle skill is outside `evidence/`.
- Compiled possible-answer files cover every task.
- Replay executes r- and r+ traces against local regime backends.
- Affected tasks have equal final states but lower r+ optimal cost.
- Unchanged, boundary, and matched-null controls do not acquire collateral
  optimal-cost changes.
- Construction report leaves unmeasured empirical metrics as `null`.

## Limitations

The package is a deterministic pilot benchmark, not a measured leaderboard
calibration. Empirical metrics such as stale-skill gap, oracle accuracy, and
adaptation recovery ratio remain `null` until measured by an experiment runner.

The D4.1 package is placed directly under `data/D4.1/` because the user request
asks for that location and this checkout does not contain the guide's example
`data/C_drift_benchmark/` collection or shared `data/dataloader.py`.
