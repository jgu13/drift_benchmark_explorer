C3.2 CLI Execution Plan

Objective

Build the C3.2 CLI-semantics drift family as a self-contained benchmark package aligned with `Drift_benchmark_architecture_guide.md`.

C3.2 uses the same physical CLI event as C3.1, but allocates the drift evidence through D2 and D3:

--path -> --root
-l -> --lines
copy-as added as lower-cost shortcut

D1 = 0%
D2 = 50%
D3 = 50%

No D1 changelog is learner-visible.

Drift Definition

The stale `r_minus` CLI supports:

find --path <dir> --name <name>
wc -l <file>
cp <src> <dst>
mv <src> <dst>
cat <file>
sort <file>

The current `r_plus` CLI supports:

find --root <dir> --name <name>
wc --lines <file>
copy-as <src> --to <dir> --name <new>
cp <src> <dst>
mv <src> <dst>
cat <file>
sort <file>

Atomic changed obligations:

R1: find root flag remap. `--path` is obsolete; `--root` is current.
R2: wc line flag retirement. `-l` is obsolete; `--lines` is current.
R3: copy-as shortcut. `copy-as` creates a renamed copy and is cheaper than cp+mv.

Final filesystem and output semantics remain stable unless the submitted command uses obsolete or invalid syntax. For R3, semantic correctness can match across regimes while the optimal current-regime cost target changes.

Evidence Allocation

D2 receives R1 and has 50% allocation. It contains exactly one success and one failure trajectory for the same atomic rule:

success: find --root . --name test_document.txt
failure: find --path . --name test_document.txt

D3 receives R2 and R3 and has 50% allocation. It provides metered current-regime probes only:

R2 stale probe: wc -l summary.txt
R2 confirming probe: wc --lines summary.txt
R3 old route probe: cp summary.txt archives/ ; mv archives/summary.txt archives/final_summary.txt
R3 shortcut probe: copy-as summary.txt --to archives --name final_summary.txt

Every D3 probe record includes `probe_id`, `rule_id`, `state_before`, `action`, `arguments`, `response`, `state_after`, and `cost`. D3 evidence must be disjoint from evaluation siblings and must not expose the oracle skill or gold traces.

Sibling Construction

Build exactly 19 evaluation siblings:

8 affected
4 unchanged-retention
4 boundary/open-set
3 matched-null

Use underscore-delimited stable IDs:

C3.2_aff_001 ... C3.2_aff_008
C3.2_ret_001 ... C3.2_ret_004
C3.2_bnd_001 ... C3.2_bnd_004
C3.2_null_001 ... C3.2_null_003

Affected coverage:

3 find-remap
2 wc-deprecation
2 copy-as efficiency
1 compound

Unchanged-retention siblings use unaffected `cat`, `sort`, primitive `cp`, and primitive `mv`. Boundary/open-set siblings exercise obsolete syntax, invalid shortcut scope, and grammar edges. Matched-null siblings vary filenames, directories, and wording without changing the current rule trace.

Mark a sibling affected from executable obligation support:

affected = (
    gold_or_optimal_trace_intersects_changed_obligation
    or graded_final_output_differs
    or current_optimal_cost_target_changes
)

Each task stores paired `r_minus_ground_truth` and `r_plus_ground_truth`, an initial filesystem state, and the expected final state or output needed by replay validation.

Compilation

`compile_c3_2.py` loads `siblings.json` and writes:

possible_answer_r_minus.json
possible_answer_r_plus.json

The possible-answer files are package-level loader-facing regime answers. C3.2 does not use a repository-level BFCL gold mirror unless a future shared loader requires one.

Recommended command:

python data/C_drift_benchmark/C3.2/cli_semantics/compile_c3_2.py --write

Limitations

This pilot is deliberately small and should not be treated as an empirical calibration. Metrics in `construction_report.json` that were not measured must remain `null` or explicitly marked as not measured. The package provides a self-contained CLI/filesystem simulator rather than importing upstream BFCL runtime code.

Validate:

  • oracle correctness on all valid siblings;
  • a non-trivial stale-skill gap on affected siblings;
  • no evidence/evaluation sibling overlap;
  • one-to-one evidence-rule coverage;
  • no collateral damage on unchanged-retention siblings;
  • correct behavior on boundary/open-set tasks;
  • no persistent edit on matched-null tasks;
  • replayability of every D2 trajectory and D3 probe;
  • exact 8/4/4/3 slice counts;
  • no fabricated empirical metrics.

Primary grading is semantic output/end-state success. Exact trajectory match is diagnostic unless the family explicitly evaluates route cost or invalid actions.
