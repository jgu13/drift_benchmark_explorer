C1.2 — BFCL Device-Enum Drift: Rebuild Execution Plan

Objective

Rebuild a **design-level C1.2 drift instance** from BFCL using an existing enum-bearing `VehicleControlAPI` task.

C1.2 tests whether an agent can migrate a persistent executable skill after a private API enum changes.

The simplest pilot uses BFCL task:

multi_turn_base_95

and the operation:

VehicleControlAPI.startEngine

The semantic task remains:

start the engine

while the private executable token changes:

r-: START
r+: X7

The final desired environment state remains:

engineState = "running"

C1.2 is a **D1-only evidence condition**:

D1 = 100%
D2 = 0%
D3 = 0%

The learner must update the stale skill from a changelog/declaration rather than from demonstrations or probing.

This first package is a **minimal design-level proof of concept**, not yet the full 25%-scope C1.2 benchmark family.

2. Inspect the executable BFCL functions

Verify the original function schema:

bfcl_eval/data/multi_turn_func_doc/vehicle_control.json

The relevant original parameter is:

startEngine.ignitionMode

with current BFCL documentation exposing:

["START", "STOP"]

Also inspect:

bfcl_eval/eval_checker/multi_turn_eval/func_source_code/vehicle_control.py

The relevant `startEngine` behavior is:

if ignitionMode == "START":
    self.engine_state = "running"

The original `startEngine` also requires:

all doors locked
brake pedal pressed
brake force = 1000.0
sufficient fuel

Verify:

pressBrakePedal(pedalPosition=1.0)

produces:

brakePedalStatus = "pressed"
brakePedalForce = 1000.0

Therefore the baseline procedural chain is:

pressBrakePedal(1.0)
        ↓
startEngine("START")
        ↓
engineState = "running"

---

3. Rewrite the user task semantically

The user prompt must **not expose the private token**.

Do not use:

"start the engine in START mode"

Use:

"I've secured all doors and engaged the parking brake.
Please start the engine."

The prompt should specify the semantic goal only.

Create `task.json` with this semantic wording.

---

4. Hide the private enum from task-level function documentation

The persistent skill should carry the private executable mapping.

Remove:

[Enum]: ["START", "STOP"]

from the learner-visible `startEngine` schema.

Create:

function_doc.json

with conceptually:

{
  "name": "startEngine",
  "description": "Starts the engine of the vehicle.",
  "parameters": {
    "type": "dict",
    "properties": {
      "ignitionMode": {
        "type": "string",
        "description": "The private ignition mode token used by the vehicle control system."
      }
    },
    "required": ["ignitionMode"]
  }
}

Do not expose either `START` or `X7` through normal task documentation.

---

5. Define regime `r-`

Create:

regime_r_minus.json

Example:

{
  "regime": "r_minus",
  "source_task": "BFCL_v4 multi_turn_base_95",
  "semantic_goal": "start_engine",
  "private_mapping": {
    "start_engine": "START"
  },
  "final_state": {
    "engineState": "running"
  }
}

The executable backend under `r-` should retain:

if ignitionMode == "START":
    self.engine_state = "running"

---

6. Create the stale skill `S-`

Create:

skill_r_minus.md

Use:

# VehicleControlAPI Skill — Regime r-

To start the vehicle engine:

1. Fully press the brake pedal:
   `pressBrakePedal(pedalPosition=1.0)`

2. Start the engine using:
   `startEngine(ignitionMode="START")`

This is the correct persistent skill before drift.

---

8. Introduce the physical drift

Create `r+` by changing **one private executable mapping only**.

Use an opaque token:

START → X7

Do not use a semantically guessable replacement such as `IGNITE`.

Keep all of the following unchanged:

user intent
function name
parameter name
brake precondition
door precondition
fuel precondition
desired final state

Only change the `start_engine` private token.

---

9. Define regime `r+`

Create:

regime_r_plus.json

Example:

{
  "regime": "r_plus",
  "source_task": "BFCL_v4 multi_turn_base_95",
  "semantic_goal": "start_engine",
  "private_mapping": {
    "start_engine": "X7"
  },
  "drift": {
    "operator": "enum_remap",
    "schedule": "abrupt",
    "changes": [
      {
        "semantic_intent": "start_engine",
        "old_token": "START",
        "new_token": "X7"
      }
    ]
  },
  "final_state": {
    "engineState": "running"
  }
}

The executable `r+` backend should use:

if ignitionMode == "X7":
    self.engine_state = "running"

and reject:

startEngine(ignitionMode="START")

as invalid.

---

10. Keep the old skill stale after drift

After the environment changes to `r+`, the learner should initially still possess:

skill_r_minus.md

which says:

start_engine → START

Thus:

Environment = r+
Persistent skill = S-

Expected stale behavior:

skill says START
        ↓
agent calls START
        ↓
r+ expects X7
        ↓
failure

Do not silently replace `skill_r_minus.md` with the new mapping.

---

11. Create the D1 changelog

C1.2 is the declaration-only evidence setting.

Create:

changelog_D1.md

Example:

# VehicleControlAPI v2 Changelog

Effective immediately:

- The private ignition token for starting the engine has changed from
  `START` to `X7`.

All other engine-starting procedures and preconditions remain unchanged.

This is the **only source of new-regime information** in the minimal C1.2 pilot.

Do not provide:

D2 demonstrations
D3 probe outcomes
rich environment error hints

---

12. Prevent accidental D3 leakage

If the learner calls:

startEngine(ignitionMode="START")

under `r+`, avoid returning an error such as:

"START is invalid. Use X7."

That would create D3 evidence.

Use only a generic result such as:

{
  "error": "Invalid ignition mode."
}

The learner should recover `X7` from the D1 changelog, not from environment feedback.

---

15. Define the expected skill update

The learner receives:

+

16. Define the core conditions

A. Before drift

Environment = r-
Skill = S-

START is correct
→ PASS

B. After drift with stale skill

Environment = r+
Skill = S-

skill calls START
environment expects X7
→ FAIL

C. After drift + D1 update

Environment = r+
Initial skill = S-
Evidence = changelog_D1.md

START → X7
→ update skill
→ PASS

D. Oracle

Environment = r+
Skill = S+ oracle

X7
→ PASS

E. No-skill control

Environment = r+
Skill = none

Because `X7` is opaque and hidden from prompt/schema, a no-skill agent should not reliably infer it.

17. Expand from one task to siblings

After approval of the one-entry pilot, construct multiple sibling tasks sharing the same regime.

Examples:

Start the engine before beginning navigation.
Start the engine and then check tire pressure.
Prepare the car and start the engine.

All depend on:

semantic obligation = start_engine

but should not repeat the D1 changelog.

Each task should include:

{
  "id": "C1.2-aff-001",
  "semantic_goal": "start_engine",
  "obligation_support": ["start_engine"],
  "slice": "affected"
}

---

18. Add unchanged-retention siblings

Once more enum obligations are included, create tasks that use unaffected mappings.

These test collateral damage.

The updated skill should preserve unaffected mappings exactly.

---

19. Add boundary/open-set siblings

Create semantic requests for unsupported device states.

Correct behavior should be:

unsupported / abstain

rather than guessing a private token.

---

20. Add matched-null siblings

Change surface wording while keeping semantic obligation identical.

Example:

"Please start the engine."

versus:

"Get the engine running."

No persistent skill update should occur merely because wording changes.

---

21. Scale to the full C1.2 physical event

The full C1.2 design should eventually include:

approximately 25% enum remapping
+
one deprecated old enum

To scale:

  1. enumerate 8–12 executable semantic enum obligations from BFCL;
  2. select approximately 25% to change;
  3. remap them to opaque tokens;
  4. explicitly retire one old token;
  5. keep all semantic outcomes fixed;
  6. generate paired `r-` and `r+` gold calls automatically.

C1.2 should remain:

D1 = 100%
D2 = 0%
D3 = 0%

The changelog must completely identify the changed mappings.

23. Validation checks

Oracle correctness

`S+` should solve the `r+` affected siblings.

Stale-skill gap

`S-` should fail or incur invalid actions on `r+` affected siblings.

Need gap

The no-skill condition should perform materially worse than `S+`.

Entry recovery

After reading the changelog, the learner should recover all changed enum rows.

Invalid-action rate

Track calls using stale/invalid enum values.

Collateral damage

Unchanged mappings should remain correct after update.

Open-set behavior

Unsupported semantic intents should not cause invented private tokens.

---

27. Agent completion checklist

An agent rebuilding C1.2 should finish only when all of the following are true:

  • [ ] one BFCL enum-bearing source task has been selected;
  • [ ] user wording contains semantic intent only;
  • [ ] learner-visible tool docs hide current private enum values;
  • [ ] `r-` executable mapping is defined;
  • [ ] `skill_r_minus.md` correctly solves `r-`;
  • [ ] `r+` changes only the intended private mapping;
  • [ ] final semantic state is identical across regimes;
  • [ ] stale `S-` is retained after drift;
  • [ ] a complete D1 changelog identifies the new mapping;
  • [ ] no D2 evidence is provided;
  • [ ] no D3 evidence leaks the replacement;
  • [ ] `skill_r_plus_oracle.md` is created but hidden from the learner;
  • [ ] paired gold calls are defined;
  • [ ] the expected update is a local enum-table patch;
  • [ ] no empirical metrics are fabricated before execution.
