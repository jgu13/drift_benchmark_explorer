# C2.1 — BFCL Precondition-Graph Drift: Agent Execution Plan

## Objective

Build an executable, BFCL-derived **C2.1 precondition-graph drift family**.

The family tests whether an agent can update a persistent procedural skill when hidden action prerequisites change.

The persistent skill stores:

```text
directed action-precondition graph
+
planner / execution recipe
```

The learner uses this graph to:

```text
topologically order required actions
+
avoid redundant calls
```

The physical drift is:

```text
edge_add + edge_drop
```

with:

```text
topology = expansion + retirement
schedule = abrupt
```

The C2.1 evidence contract is:

```text
D1 = 0%
D2 = 40%
D3 = 60%
```

where:

```text
D2 = successful post-drift sibling traces
D3 = violation / counterexample interaction feedback
```

The full family should support a drift-scope sweep over:

```text
10%
25%
40%
```

of **performance-relevant precondition edges**.

The initial construction target is:

```text
72 total siblings

32 affected
18 unchanged-retention
14 boundary/open-set
8 matched-null
```

For the first pilot, implement only a small subset, but preserve the same construction logic.

---

# 1. Reuse the same physical event as C2.2

C2.1 and C2.2 use the **same `r- → r+` environment change**.

Their difference is:

```text
C2.1:
D2 = 40%
D3 = 60%

C2.2:
D2 = 0%
D3 = 100%
```

Therefore do not invent a different graph event for C2.1.

Use the same BFCL `VehicleControlAPI` substrate and the same pilot physical event:

```text
ADD:
parking brake engaged → start engine

DROP:
full brake pedal → start engine
```

This makes C2.1 and C2.2 directly comparable.

# 4. Define the graph representation

Represent the skill as a directed graph over:

```text
action nodes
+
state-predicate nodes
```

Recommended action nodes:

```text
A_lock
A_brake
A_park
A_fuel
A_start
A_cruise
```

Recommended predicate nodes:

```text
P_doors_locked
P_brake_full
P_parking_brake_engaged
P_fuel_available
P_engine_running
```

An edge:

```text
P_brake_full → A_start
```

means:

> the full-brake predicate must hold before `startEngine` is valid.

An edge:

```text
A_start → P_engine_running
```

means:

> successful engine start establishes the engine-running predicate.

# 8. Build executable regime `r+`

Copy:

```text
vehicle_control_c2_r_minus.py
```

to:

```text
vehicle_control_c2_r_plus.py
```

Modify only the chosen prerequisite edges.

## Remove the retired edge

Disable the brake-pedal prerequisite for engine start.

For example, remove:

```python
if self.brakePedalStatus != "pressed":
    return {"error": ...}

if self._brakePedalForce != 1000.0:
    return {"error": ...}
```

from the `r+` start procedure.

## Add the new edge

Add:

```python
if self.parkingBrakeStatus != "engaged":
    return {
        "error": "Parking brake must be engaged before starting the engine."
    }
```

Keep unchanged:

```text
door requirement
fuel requirement
engine-start effect
cruise-control semantics
unrelated vehicle actions
```


# 27. Prevent D2 from identifying the entire graph

D2 should cover only its assigned 40% edge weight.

Do not provide successful traces for every edited configuration.

In particular, successful traces alone may not prove that:


was retired.

A trace that omits a brake action is evidence, but retirement should be made causally decisive through D3 counterexamples or controlled comparisons.

This preserves meaningful D3 responsibility.

# 33. Require candidate-plan replay before skill promotion

After the learner proposes a graph update:

1. generate a candidate plan from the updated graph;
2. execute it in the `r+` simulator;
3. verify final state;
4. verify no invalid actions;
5. compare its cost against the oracle minimal plan;
6. only then promote the new graph into persistent skill.

Do not accept a text-only graph edit without executable replay.

```python
    set(task.obligation_support)
```

```text

```

If unaffected:

```text

```

Do not manually relabel tasks based on intuition.
