# D4.2 BFCL Execution Plan

## Objective

Build an AppWorld-pattern D-family efficiency-drift benchmark where a better
path appears after a regime update, and the learner receives D2 and D3 evidence
instead of a D1 changelog.

```text
Benchmark ID: D4.2
Semantic package: bulk_tag_app
Drift: action_add
Topology: improvement
Schedule: abrupt
Physical event: one new bulk endpoint replaces 3-5 primitive calls
Evidence allocation: D1 = 0%, D2 = 50%, D3 = 50%
```

The stale route remains semantically correct. Adaptation should infer the new
bulk action from observed trajectories and probe evidence, then cost-gate its
use only when the endpoint is in scope.

## Drift Definition

Use the same deterministic contact/tag API as D4.1.

`r_minus` exposes:

```text
get_contact(contact_id)
add_tag(contact_id, tag)
remove_tag(contact_id, tag)
```

`r_plus` preserves all stale endpoints and adds:

```text
bulk_add_tag(contact_ids, tag)
```

The new endpoint is valid only when:

```text
3 to 5 contact IDs are supplied
all contacts belong to the same workspace
the list contains no duplicate IDs
one shared tag is applied to all listed contacts
```

Cost model:

```text
get_contact = 1
add_tag = 1
remove_tag = 1
bulk_add_tag = 1
```

For 3-5 valid same-workspace contacts, the post-drift optimum is one
`bulk_add_tag` call instead of 3-5 `add_tag` calls. Final semantic state is
identical across regimes.

## Evidence Allocation

Learner-visible evidence is restricted to `bulk_tag_app/evidence/`.

```text
D1: none
D2: evidence/d2_success_trajectories.jsonl
D2: evidence/d2_failure_trajectories.jsonl
D3: evidence/d3_probe_log.jsonl
```

`skill_r_minus.md` is learner-visible stale skill text. `skill_r_plus_oracle.md`
is hidden evaluation-only oracle text and must not be exposed as evidence.

For the single changed obligation `E01`, D2 must contain exactly one success
trajectory and one failure trajectory. Both records include an explicit
`revealed_rule` field:

```text
bulk_add_tag(contact_ids, tag) is valid for 3-5 unique same-workspace contacts sharing one tag.
```

The D2 success trajectory uses the new endpoint correctly. The D2 failure
trajectory violates the same endpoint scope and is replayable against the
current regime. D3 provides a disjoint evidence-only probe showing identical
final state and strictly lower metered cost, plus an idempotence probe for an
already-tagged contact.

## Sibling Construction

Use `siblings.json` as the canonical task source in manifest form. Build exactly
19 evaluation siblings:

```text
8 affected
4 unchanged-retention
4 boundary/open-set
3 matched-null
```

Use stable underscore-delimited IDs:

```text
D4.2_aff_001 ... D4.2_aff_008
D4.2_ret_001 ... D4.2_ret_004
D4.2_bnd_001 ... D4.2_bnd_004
D4.2_null_001 ... D4.2_null_003
```

Each sibling must include:

```text
id
slice
semantic_goal
obligation_support
question
initial_state
involved_classes
affected
r_minus_ground_truth
r_plus_ground_truth
expected_final_state
expected_cost_r_minus
expected_cost_r_plus
```

Mark affectedness from executable obligation support rather than wording:

```python
affected = (
    gold_or_optimal_trace_intersects_changed_obligation
    or graded_final_output_differs
    or current_optimal_cost_target_changes
)
```

Affected siblings cover 3-5-contact same-tag goals and compound workflows where
the final state is unchanged but the optimal post-drift cost decreases.
Unchanged-retention siblings cover 1-2 contact adds, tag removal, and read-only
lookup. Boundary/open-set siblings cover six contacts, mixed workspaces, empty
lists, and duplicates. Matched-null siblings vary wording/order/IDs without a
bulk-applicable optimal-cost change.

## Compilation

`compile_d4_2.py` loads `siblings.json`, validates the 8/4/4/3 composition,
and writes:

```text
possible_answer_r_minus.json
possible_answer_r_plus.json
optimal_costs.json
sibling_summary.json
```

Package-level `possible_answer_*` files are the loader-facing answer files.
This repository does not currently include `data/dataloader.py`; if a shared
drift loader is later added, register `D4.2` to point at:

```text
D4.2/bulk_tag_app/siblings.json
```

## Validation

Run:

```bash
python data/D4.2/bulk_tag_app/compile_d4_2.py --write
python data/D4.2/bulk_tag_app/validation/replay_checks.py
bash data/D4.2/bulk_tag_app/validation/test_d4_2_architecture.sh
```

Validation must check:

- JSON parseability for all package JSON artifacts.
- `siblings.json` is a manifest with 19 tasks.
- Exact slice counts are 8/4/4/3.
- All task IDs use the `D4.2_<slice>_<nnn>` convention.
- `r_plus` preserves stale actions and adds only `bulk_add_tag`.
- No D1 evidence files exist.
- D2 success and failure trajectory files are present and replayable.
- D3 probe evidence is present and named with a `d3` prefix.
- `evidence_allocation.json` states D1=0, D2=50, D3=50.
- The oracle skill is outside `evidence/`.
- Compiled possible-answer files cover every task.
- Replay executes r- and r+ traces against local regime backends.
- Affected tasks have equal final states but lower r+ optimal cost.
- Unchanged, boundary, and matched-null controls do not acquire collateral
  optimal-cost changes.
- Construction report leaves unmeasured empirical metrics as `null`.

## Limitations

The package is a deterministic pilot benchmark, not a measured leaderboard
calibration. Empirical metrics such as stale-skill gap, oracle accuracy, and
adaptation recovery ratio remain `null` until measured by an experiment runner.

The D4.2 package is placed directly under `data/D4.2/` because the user request
asks for that location and this checkout does not contain the guide's example
`data/C_drift_benchmark/` collection or shared `data/dataloader.py`.
